# 在项目台账中使用 Git

Git 保存文件版本与差异。台账保存变更原因、实际验收、运行观察和恢复步骤。可以先用本地仓库。已有台账和备份足以支持当前工作时，继续按原方式记录即可。

## 先确定仓库和纳管范围

1. 在目标目录用 `git rev-parse --show-toplevel` 核对仓库根，再查看 `git status --short`。目录在上级仓库内时，先确认应该沿用哪一层。目标没有仓库且用户授权建立时，再初始化。已有仓库沿用其分支、忽略规则和作者设置；缺少作者信息时询问，保留已有配置。
2. 优先纳入规则、状态、使用文档、项目维护的源文件、启动脚本、配置与脱敏后选定的工作日志。按用途区分顶层日志和同名附件目录。模型权重、安装包、构建产物、运行日志、大型夹具和原始备份一般保存在仓库外。凭据、认证材料和私有数据使用受保护的位置。项目目录外的部署文件用台账和备份记录。
3. 先审阅候选清单，再按授权设置忽略规则。用 `git check-ignore -v -- <路径>` 解释忽略项，用 `git ls-files -- <路径>` 检查是否已跟踪。忽略规则不会移除已跟踪文件，也不会清理历史中的秘密。发现既有敏感跟踪项时，单独记录并按授权处理。

## 留基线和日常提交

1. 有 Git 的项目先找最近可用版本，记录提交号和关键路径。新建仓库时，若用户也授权首批提交，可在迁移或变更前只提交审核过的原文件，形成改前基线。基线和本次变更分别提交。没有可用的已提交版本时，按项目规则保存改前副本。
2. 修改后用 `git diff -- <路径>` 看已跟踪文件的未暂存差异，用 `git status --short` 找新增文件并单独审阅内容。只按明确路径暂存，使用 `git add -- <路径>`。共享文件混有他人改动时，保留这些改动，按本次范围分块或先协调。已有无关暂存内容时先协调，避免把它一起提交。
3. 提交前用 `git diff --cached --name-status` 和 `git diff --cached` 核对实际暂存清单与差异，检查大文件、私有材料和意外改动。获授权后按一个可独立说明和验证的目标提交。台账记录提交号、关键路径、实际验证及遗留项。初始化、暂存、提交和推送按实际授权范围执行，远程与共享另行确认。

## 查看旧版和恢复

- 用 `git diff <基线提交> -- <路径>` 查看该路径相对基线的已跟踪差异，用 `git show <基线提交>:<仓库内路径>` 只读查看旧文件。比较前先确认该基线对应的实际验收范围。
- 获授权后按受影响的文件或变更范围恢复，先保护当前工作和未提交改动。需要撤销整次独立提交时，先评估后续依赖，再按项目流程用反向提交保留历史。
- Git 恢复的是纳入版本管理的文件。对于已启动服务、目录外文件和未纳管数据，按工作日志核对现场及对应备份，并在授权范围内验证实际恢复结果。
